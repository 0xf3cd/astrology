# 参与开发

[English](../en/contributing.md) · [文档入口](index.md)

先读相关 issue 和[结构设计](architecture.md)。issue 定义功能范围与验收案例，
每次改动应能作为一个行为变化讲清楚、审清楚。

PR、issue、评论与审阅回复使用英文，标题也用英文。文档以英文为主，并维护对应中文页面。

## 运行检查

安装 [uv](https://docs.astral.sh/uv/getting-started/installation/)，在仓库根目录运行：

```sh
uv sync --locked --python 3.14
uv run --locked python tools/check.py
```

支持 Python 3.11–3.14，下限与 celestial-calendar 0.8.0 一致；该库是本包的硬依赖。
CI 在 Linux 3.11／3.14 和 macOS／Windows 3.14 上运行同一命令。
本地验证下限时使用 `uv sync --locked --python 3.11`。

天文依赖只发布 Linux x86_64 与 aarch64、macOS 14+ arm64、Windows amd64 的轮子，没有源码分发包。
因此本包在其他平台无法安装，浏览知识目录也需要同样的安装。

该命令检查 Ruff lint／两空格格式、严格 mypy、普通与优化模式下的 pytest、文档对页／本地链接、
从头生成的严格 HTML／doctest 构建及带声明运行依赖的隔离 wheel 安装。
`python -m build` 经 sdist 构建 wheel；安装后的消费者程序在仓外验证出生、时区来源与配置。
另有仅查知识的消费者，执行列举、名称查询、筛选及引用解析，不初始化时间或原生库。
两者均以隔离导入运行普通与优化模式；wheel 和 sdist 检查要求实际包含语料资源。
临时 HTML、doctest 报告、分发包和消费者环境优先使用 `SCRATCH`，否则使用系统临时目录，
退出时删除。构建元数据和工具缓存可能保留在仓内已忽略的目录中。

工具版本由 `uv.lock` 锁定：Python 3.11 使用 Sphinx 8.2.3，较新 Python 使用 Sphinx 9.1.0。
覆盖率报告用于定位遗漏，但不能认证天文数值，那由参考案例负责。测试覆盖出生／时刻与配置合同，以及开发检查；领域测试随功能加入。

本地格式化运行 `uv run ruff format .`。任一命令失败即停止，修复原因后重跑。
依赖变更须更新锁文件并通过两个 Python 端点；忽略规则或警告时应限制范围并说明原因。

若要保留 HTML 供检查，可构建到已忽略的 `build/` 目录：

```sh
uv run python -m sphinx -E -a -n -W -b html -c docs . build/docs
```

打开 `build/docs/docs/index.html`，可进入两种语言。共用索引保留英文词干处理，
Python 与 JavaScript 使用对应的中文相邻双字切分。限制见[知识指南](knowledge.md#译文修订与搜索)。
检查核实际生成的搜索索引、输出的分词及词干接口、页面语言与对页导航、完整目录锚点及当前译文。
构建成功不能代替这些检查。独立核验可以执行生成的 JavaScript 查询及索引代码；
Python 分词单测不能证明浏览器行为。

按上面的 `uv sync` 从本仓安装开发包，本地分发名／版本为 `astrology`／`0.0.0`。
PyPI 的 `astrology` 属于另一个无关项目；首次发布前须确定发布名。
可检查已安装的开发版本：

```{doctest}
>>> from importlib.metadata import version
>>> version("astrology")
'0.0.0'
```

## 设计

输入、配置、规则和结果默认采用不可变值。冻结 dataclass 仍不能冻结内部的列表或字典；
使用不可变成员，或在边界复制并隔离可变输入。调用方在构造后改动原始输入，不应改变已存命盘。

优先使用参数和返回值明确的普通函数。文件读取、原生库初始化、网络调用与缓存由所属边界显式负责。
导入包或查知识不应触发排盘。

表格形规则用数据表达，计算用函数表达。定义归领域模块，入口负责组合。
有真实调用方共用一个合同再提取抽象，潜在的未来后端不算调用方。
含义尽量进入名字与类型，再由注释补充理由。

配置必须影响它所描述的计算。拒绝不支持的选择，保留请求和实际生效配置。
避免隐式全局设置、静默替代，以及返回类型依赖隐藏状态的工厂。

## 正确性

除代表值外，还要测试领域边界：非有限数、时间歧义、坐标回绕、精确端点、缺失信息与不支持的组合。
公开输入校验在 `python -O` 下也必须有效。

数值夹具记录来源、模型／版本、时标、坐标口径、配置、单位和容差。
往返测试检验保真，重新计算检验执行，独立来源检验一致性。共用公式或复制的数据集
可能让多份检查在同一错误上相互吻合；说明参考案例为什么能发现要测的缺陷。

示例使用合成数据或允许转载的来源。天文数值的验证与命盘解读的主张分别处理。

`tests/reference/natal_reference.json` 中的本命盘案例覆盖南北半球各一个时刻，
与 JPL Horizons 及定义级检查比对。夹具记录查询 URL、Horizons 为每个天体及地心给出的
星历核（太阳、月亮、水星与金星用 DE441，其余天体用各自的核）、取数时间及所用口径。

天体容差取自上游模型对 Horizons 的自身误差，而不是这两个时刻。太阳与行星在
2000—2002 年 24 个时刻的经度一致到约 0.8 角秒，在 2020 年夹具时刻为 1.3；
截断的月历模型在 2000—2030 年 60 个时刻的经度一致到 10 角秒、黄纬到 2.4。
这些采样是临时测量，没有留在仓库里。容差为：太阳与行星 3 角秒，月亮 15 角秒，
黄纬 1 角秒，月亮黄纬 3 角秒，交点 1 角秒。四轴与 Placidus 宫头用 0.001 度（3.6 角秒）：
两个时刻在此最多相差 0.91 角秒，这是本库模型 UT1 与 Horizons 观测 UT1 之差。

各条参考检出的缺陷不同。缺陷能否被抓到，取决于容差与库本来就和参考相差多少（四轴至多 0.91 角秒，
月亮经度 3.4），所以略低于容差的偏移也可能被抓到。下面各例都按计入这个偏差来判：

| 参考 | 能检出 | 检不出 |
|---|---|---|
| Horizons 黄经 | 星历错误或天体映射错误。用 UTC 代 TT（差 64—69 秒）使月亮偏 35—42 角秒、水星偏 3—5。 | 计入该偏差后仍在容差内的偏移，包括只破坏太阳的路径（偏 2.6—2.8 角秒）。 |
| 精确的闰秒关系 | 把 UTC 或 UT1 当作 TT：报告的 JDE(TT) 偏 0.2—0.3 秒。 | 把 UTC 当 UT1 的自转路径；报告的 JDE(TT) 仍然精确。 |
| Horizons 恒星时，四轴 | 用平恒星时代替真恒星时（偏 0.002—0.005 度）。把 UT1 取作 UTC：北例偏 5.0 角秒，南例 3.7，南例只是刚过 3.6 的阈值。北例用平黄赤交角代真黄赤交角（偏 5.7）。 | 南例用平黄赤交角代真黄赤交角（偏不到 1 角秒）。 |
| Horizons 恒星时，Placidus 第 2、3、11、12 宫头 | 宫头偏离 Placidus 时间分割超过约 0.0015 度，例如换成别的宫制。 | 与检查共有的对 Placidus 定义的误读。第 5、6、8、9 宫头只作为精确对冲核对；仓库里没有宫头的外部参考值。 |
| Meeus 第 47 章交点 | 交点定义、方向错误或漏掉章动项。 | 共用公式里的错误，以及 TT／UT 混用（交点只偏不到 0.4 角秒）。 |

相位的检查分三层。`tests/test_aspects.py` 里手算的案例不需要天文计算。取一小时的差商核对报告出的
黄经，用来确认入相／离相状态背后的速率符号和单位正确。参考测试按 Astrodienst 为 Hellenistic 绘图风格
公布的容许度配置本库，把求出的相位集合与由 Horizons 黄经推出的集合比较。它们能检出错误的容许度、
合成规则、落在限度附近的错误角度，以及参与相位的月交点；检不出小于 0.4 度余量的黄经误差，
也不拿外部来源核对状态：这里 Horizons 不提供速率，Astrodienst 公布的是参数，不是某张盘的相位表。

## 知识与文档

遵循[知识设计](knowledge.md)，解释文字链接稳定的概念、规则与来源标识。
保留原文并标明译文；来源已核实，不能证明某张盘满足条目前提。

行为变化时同步更新两种语言。公开 docstring 的概述和合同保留双语；标识、签名、单位、
默认值只有一份来源。运行例子并检查生成页面。自动检查能发现缺少译文文件，但不能证明译文语义相同。
目录检查还拒绝旧译修订、记录说明缺失、未知引用及重复标识。两种语言均有可执行例子；
来源及翻译审阅检查前提与限度是否保真。

## 审阅依据

使用 AI 编写的贡献仍由贡献者负责。在 PR 中说明对应 issue、行为变化、实际运行的检查和未解决问题，
区分已经执行的验证与建议以后运行的检查。

审阅检查来源是否忠实、假设是否成立、对象修改与共享、失败行为、抽象是否多余及翻译语义。
lint 通过或覆盖率很高不能回答这些问题。修改检查程序时，同时提供应通过的输入与应拒绝的缺陷。

合并和发布需要维护者批准。CI 负责报告检查结果；若要自动阻止未通过检查的合并，
还需在仓库规则中将它们设为必需检查。
