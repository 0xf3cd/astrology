参与开发¶

English · 文档入口

先读相关 issue 和结构设计。issue 定义功能范围与验收案例， 每次改动应能作为一个行为变化讲清楚、审清楚。

PR、issue、评论与审阅回复使用英文，标题也用英文。文档以英文为主，并维护对应中文页面。

运行检查¶

安装 uv，在仓库根目录运行：

uv sync --locked --python 3.14
uv run --locked python tools/check.py

支持 Python 3.11–3.14，下限与 celestial-calendar 0.8.0 一致；该库是本包的硬依赖。 CI 在 Linux 3.11／3.14 和 macOS／Windows 3.14 上运行同一命令。 本地验证下限时使用 uv sync --locked --python 3.11。 开发检查使用当前补丁版。检查中的 sdist 安全解压要求 Python 3.11.4 或更高版本； 安装后库的次版本支持范围仍为 3.11–3.14。

天文依赖只发布 Linux x86_64 与 aarch64、macOS 14+ arm64、Windows amd64 的轮子，没有源码分发包。 因此本包在其他平台无法安装，浏览知识目录也需要同样的安装。

该命令检查 Ruff lint／两空格格式、严格 mypy、普通与优化模式下的 pytest、文档对页／本地链接、 从头生成的严格 HTML／doctest 构建及带声明运行依赖的隔离 wheel 安装。

分发检查先运行 python -m build --sdist 并解压归档，再在解压目录运行 python -m build --wheel。 严格 HTML／doctest 构建也在该目录运行，导入其中的包源码。随后检查 API／知识目录页面、 生成的搜索索引及查询代码，以及 doctest 结果。

安装后的消费者程序在仓外验证出生、时区来源与配置。 完整盘、原始结果对照及文本检查见结果指南。 另有仅查知识的消费者，执行列举、名称查询、筛选及引用解析，不初始化时间或原生库。 两者均以隔离导入运行普通与优化模式；wheel 和 sdist 检查要求实际包含语料资源。

临时 HTML、doctest 报告、分发包和消费者环境优先使用 SCRATCH，否则使用系统临时目录， 退出时删除。构建元数据和工具缓存可能保留在仓内已忽略的目录中。 严格文档构建可能从 docs.python.org 获取 Python intersphinx 清单；除安装构建依赖外，还需允许联网。

CI 安装 uv 0.12.5，按平台归档使用其上游发布 的 SHA-256 摘要。安装步骤使用新的工具缓存目录，避免 setup-uv 命中缓存后跳过归档校验。

uv、setup-uv 或 runner 平台变化时，在临时分支复验反例：把矩阵中每个 uv-checksum 改为带引号的 64 个零字符串并推送。每个 setup-uv 步骤都应以摘要不匹配报错，后续 uv 命令应被跳过。 无关的下载或网络错误不能作为通过依据。不要合并该分支。

工具版本由 uv.lock 锁定：Python 3.11 使用 Sphinx 8.2.3，较新 Python 使用 Sphinx 9.1.0。 覆盖率报告用于定位遗漏，但不能认证天文数值，那由参考案例负责。 测试覆盖出生／时刻、命盘／配置、结果与文本合同，以及开发检查；领域测试随功能加入。

本地格式化运行 uv run ruff format .。任一命令失败即停止，修复原因后重跑。 依赖变更须更新锁文件并通过两个 Python 端点；忽略规则或警告时应限制范围并说明原因。

若要保留 HTML 供检查，可构建到已忽略的 build/ 目录：

uv run python -m sphinx \
  -E -a -n -W -b html -c docs \
  -d build/docs-doctrees . build/docs

打开 build/docs/index.html，可进入两种语言。共用索引保留英文词干处理， Python 与 JavaScript 使用对应的中文相邻双字切分。限制见知识指南。 检查核实际生成的搜索索引、输出的分词及词干接口、页面语言与对页导航、完整目录锚点及当前译文。 构建成功不能代替这些检查。独立核验可以执行生成的 JavaScript 查询及索引代码； Python 分词单测不能证明浏览器行为。

Sphinx 只发现根目录的两个 README 和 docs/ 下的源文档。虚拟环境应放在 docs/ 之外： 该目录内任意位置的源文档都是文档输入，与它同级的目录则不是。上述源文档中的警告仍会使严格构建失败。

按上面的 uv sync 从本仓安装开发包，分发名／版本为 celestial-astrology／0.2.0， Python 导入名仍为 astrology。PyPI 的 astrology 是另一个无关项目， 不是本库。可检查已安装的身份：

>>> from importlib.metadata import version
>>> version("celestial-astrology")
'0.2.0'

检查会在隔离的 wheel 安装环境中执行两份 README，比较文档中的输出，检查 wheel 实际保存的 Markdown 链接，并在构建后的站点中解析两种语言的路径。还会在一次性安装环境中隐藏 celestial-astrology 元数据，确认导入和知识查询仍可用，直接计算抛出指明该分发包的 PackageNotFoundError。普通／优化模式都执行，随后恢复元数据。

手动发布 Pages 时，从干净且已提交的源码构建，将 ASTROLOGY_DOCS_SOURCE_SHA 设为完整的小写提交号。 根页据此生成源码归档链接和安装命令；普通本地构建则明确没有固定版本。 doctrees、缓存及其他构建控制文件不进入站点成品。检查所有生成的源文档、下载文件和静态资源后， 再手动更新带有 .nojekyll 的独立 gh-pages 分支。这是手动更新站点，不是自动发布源码或发行包。 实际验收还须检查已部署的根页、每条 README URL 和中英文浏览器搜索，不能只看本地 HTML 构建成功。 快照安装和 Python intersphinx 索引需要联网。

设计¶

输入、配置、规则和结果默认采用不可变值。冻结 dataclass 仍不能冻结内部的列表或字典； 使用不可变成员，或在边界复制并隔离可变输入。调用方在构造后改动原始输入，不应改变命盘结果。

优先使用参数和返回值明确的普通函数。文件读取、原生库初始化、网络调用与缓存由所属边界显式负责。 导入包或查知识不应触发排盘。

表格形规则用数据表达，计算用函数表达。定义归领域模块，入口负责组合。 有真实调用方共用一个合同再提取抽象，潜在的未来后端不算调用方。 含义尽量进入名字与类型，再由注释补充理由。

配置必须影响它所描述的计算。拒绝不支持的选择，保留请求和实际生效配置。 避免隐式全局设置、静默替代，以及返回类型依赖隐藏状态的工厂。

正确性¶

除代表值外，还要测试领域边界：非有限数、时间歧义、坐标回绕、精确端点、缺失信息与不支持的组合。 公开输入校验在 python -O 下也必须有效。

数值夹具记录来源、模型／版本、时标、坐标口径、配置、单位和容差。 源码／安装包对照检验打包一致性，独立来源检验数值一致性。共用公式或复制的数据集 可能让多份检查在同一错误上相互吻合；说明参考案例为什么能发现要测的缺陷。

示例使用合成数据或允许转载的来源。天文数值的验证与命盘解读的主张分别处理。

tests/reference/natal_reference.json 中的本命盘案例覆盖南北半球各一个时刻， 与 JPL Horizons 及定义级检查比对。夹具记录查询 URL、Horizons 为每个天体及地心给出的 星历核（太阳、月亮、水星与金星用 DE441，其余天体用各自的核）、取数时间及所用口径。

若要重新取回两组 Horizons 数据而不改动已提交的夹具：

uv run --locked python tools/fetch_reference.py --output build/natal_reference.json

取数需要联网，仅依赖 Python 标准库。必须指定输出路径；工具不读取本地参考或审阅文件。 输出包含查询 URL、来源星历核、计算口径、取数时间和值，随后打印该文件的 SHA-256。 有意替换版本化夹具之前，先检查数值和来源信息的变化。离线测试使用受控响应，与真实联网取数分开。

天体容差取自上游模型对 Horizons 的自身误差，而不是这两个时刻。太阳与行星在 2000—2002 年 24 个时刻的经度一致到约 0.8 角秒，在 2020 年夹具时刻为 1.3； 截断的月历模型在 2000—2030 年 60 个时刻的经度一致到 10 角秒、黄纬到 2.4。 这些采样是临时测量，没有留在仓库里。容差为：太阳与行星 3 角秒，月亮 15 角秒， 黄纬 1 角秒，月亮黄纬 3 角秒，交点 1 角秒。四轴与 Placidus 宫头用 0.001 度（3.6 角秒）： 两个时刻在此最多相差 0.91 角秒，这是本库模型 UT1 与 Horizons 观测 UT1 之差。

各条参考检出的缺陷不同。缺陷能否被抓到，取决于容差与库本来就和参考相差多少（四轴至多 0.91 角秒， 月亮经度 3.4），所以略低于容差的偏移也可能被抓到。下面各例都按计入这个偏差来判：

基于 Horizons 和手算的相位检查分三部分。tests/test_aspects.py 用手算案例，不需要天文计算。用相隔一小时的黄经差除以时间， 核对速率的符号和单位，因为入相／离相状态依赖这些速率。参考测试按 Astrodienst 为 Hellenistic 绘图风格 公布的容许度配置本库，把求出的相位集合与由 Horizons 黄经推出的集合比较。有一对对象靠近限度时，它们能检出 错误的容许度、合成规则或角度；也能检出参与相位的月交点。检不出小于 0.4 度余量的黄经误差；两个时刻 里没有六分相和对分相，这两个角度靠手算案例核对。运动状态没有与外部结果比对：这里 Horizons 不提供 速率，该风格页公布的是参数，不是某张盘的相位表。

另设的 Swiss 完整盘夹具增加独立速率及全部宫头，还对四个合成时刻另写算术推导归属、 相位和运动状态，五种相位均有出现。各案例容差和来源限度见结果指南。 项目计算的数值回归样本不作为外部证据。修改纯规则或依赖时，保留样本原数值及提取来源。 当前来源和数值回归分别检查：仅版本号变化不能阻止数值比较； 模型发生变化时须明确适用的比较政策。

证明回归测试能接受有效输入，并拒绝它所针对的缺陷。只改版本标签应通过数值回归； 构造合法但超出容差的数值变化，必须在数值断言处失败。在 PR 中记录改过的输入或实现、 真实退出码及失败位置。构造或导入失败不能证明数值检查有效。

知识与文档¶

遵循知识设计，解释文字链接稳定的概念、规则与来源标识。 保留原文并标明译文；来源已核实，不能证明某张盘满足条目前提。

行为变化时同步更新两种语言。公开 docstring 的概述和合同保留双语；标识、签名、单位、 默认值只有一份来源。运行例子并检查生成页面。自动检查能发现缺少译文文件，但不能证明译文语义相同。 目录检查还拒绝旧译修订、记录说明缺失、未知引用及重复标识。两种语言均有可执行例子； 来源及翻译审阅检查前提与限度是否保真。

审阅依据¶

使用 AI 编写的贡献仍由贡献者负责。在 PR 中说明对应 issue、行为变化、实际运行的检查和未解决问题， 区分已经执行的验证与建议以后运行的检查。

审阅检查来源是否忠实、假设是否成立、对象修改与共享、失败行为、抽象是否多余及翻译语义。 lint 通过或覆盖率很高不能回答这些问题。修改检查程序时，同时提供应通过的输入与应拒绝的缺陷。

合并规则¶

修改 main 必须通过 PR，并满足以下四项必需检查：

  • quality (ubuntu-latest, 3.11)

  • quality (ubuntu-latest, 3.14)

  • quality (macos-latest, 3.14)

  • quality (windows-latest, 3.14)

必需检查采用严格模式，还要求分支包含 main 的最新内容。仓库配置的必需批准数为零， 但这不授权自动化 agent 自行合并；合并和发布仍须维护者批准。

分支保护也适用于管理员。当前未配置合并时的绕过权限，禁止强制推送或删除 main。 修改这些设置属于独立的管理操作，须另获维护者授权。 仓库只允许 squash 合并，提交标题和正文取自 PR 标题和正文。

安全核验保护行为时，使用绝不合并的临时非草稿 PR，在同一 PR 上依次观察 必需检查成功、仅对探针分支生效的故意失败、恢复成功。 记录受测版本、检查的准确名称和结果、当前 main 版本、生效的分支保护规则及 REST／GraphQL 合并状态，并排除冲突、落后主干或阻塞性审阅等其他原因。 仅有配置不变，不能证明实际执行行为。

mergeable 描述有无冲突，不表示允许合并。上述故意失败发生时，服务端计算的 BLOCKED 状态与实际合并请求被拒绝是两种证据。不要尝试合并故意失败的探针，或为得到预期结果而 放宽保护。有歧义的结果仍是未完成的证据；本仓合并规则的实际核验由 #15 追踪。
