Next release: v0.2.0 (unreleased)¶

Static cross-chart aspects¶

cross_chart_aspects compares two in-memory natal results with explicit rules. CrossAspectHit records static geometry with distinct left/right endpoints; CrossChartAspects retains both complete sources and the comparison request. Same-named objects and cross-chart node pairs are allowed. There is no motion field or common-epoch conversion. See the cross-chart guide.

Ashmand 1822 sign groups¶

ashmand_sign_group maps an existing Sign to an AshmandSignGroup: tropical, equinoctial, fixed or bicorporeal. The knowledge guide links the complete twelve-sign table, explains the historical names, and provides source excerpts and Chinese translations.

Breaking change: chart persistence removed¶

The next release removes dumps_chart, loads_chart, recompute_chart, ChartRecordError, ChartReplayError and the astrology.serialization module. The chart storage schema and historical-record compatibility policy are withdrawn, with no replacement format or compatibility wrapper. The package no longer reads saved chart JSON. If an application needs the old API, keep the published v0.1.0 environment; its tag and artifacts are unchanged.

Calculate with natal_chart, use its immutable in-memory NatalChart and format it with format_chart. Original/resolved birth input, requested/effective configuration, astronomical values, domain validation and calculation provenance remain. This removal does not change the astronomy, timezone policy or dependency pins.

0.1.0¶

The first release provides modern tropical, geocentric natal charts and an independently browsable English/Chinese knowledge catalog. Install the distribution celestial-astrology; Python imports remain astrology.

Delivered API¶

  • Immutable original birth records, explicit timezone interpretation, and resolved calculation instants. Unknown time or location is preserved as missing; natal preparation rejects incomplete inputs rather than supplying noon or a location.

  • Solar, lunar and planetary positions, named lunar-node definitions, axes and Whole Sign, Equal or Placidus houses. An undefined requested geometry raises ChartDomainError without selecting another house system.

  • Tropical signs, longitude-only house placement, and five major aspects with explicit orb rules and local applying/separating status. This status describes motion at the calculation instant, not a forecast of a later exact aspect.

  • Versioned chart records, restoration, explicit recomputation, and English/Chinese text output. Astronomy values, requested/effective settings and provenance remain separate in the stored result.

  • Knowledge concepts, named rule variants, aliases and citations without calculating a chart or initializing native astronomy. Source verification, prerequisite status, output eligibility and chart applicability remain distinct. Quotations, translations and project-authored explanations retain their own attribution.

The chart, aspect, v0.1.0 record and knowledge guides define the admitted conventions and corpus.

Installation and compatibility¶

Python 3.11–3.14 is supported. Runtime dependencies are exactly celestial-calendar==0.8.0 and tzdata==2026.5. Exact pins preserve the selected models and timezone data, but can prevent installation beside a consumer that requires another version. This release does not upgrade to celestial 0.9 or widen the dependency ranges.

Installation requires a compatible upstream astronomy wheel: Linux x86_64 or aarch64 with the corresponding manylinux support, macOS 14+ arm64, or Windows amd64. The astronomy dependency has no sdist. The astrology wheel’s any platform tag does not remove that restriction; knowledge-only use needs the same install.

Schema v1 restoration preserves stored values and their original provenance, including historical 0.0.0 records, without loading astronomy. Recomputation requires exact installed astrology/celestial versions and the recorded model. Restoring a historical record does not make it recomputable under 0.1.0; a version or model mismatch raises ChartReplayError. See the v0.1.0 record guide.

Verification and limits¶

The full quality workflow runs on Linux Python 3.11/3.14 and macOS/Windows 3.14. Release installation consumers use the same retained wheel on Linux x86_64 3.11/3.12/3.13/3.14, Linux ARM64 3.14, macOS ARM64 3.14 and Windows amd64 3.14. The latter seven jobs check installation and consumers; they are not full quality runs on every supported Python/platform pair. Run-specific results and artifact digests belong to the release record, not a prewritten claim that those jobs passed.

Independent JPL Horizons and Swiss reference cases use named conventions and documented tolerances. Their scope and shared-model limits are in the correctness guide. Restoration round trips and same-runner source/install comparisons check preservation; they do not replace those external references or promise cross-platform bitwise floating-point equality.

The adapter evaluates a fixed joint fourteen-object snapshot, even when a request selects fewer objects. Its admitted domain is the intersection of that snapshot’s ephemeris/time limits and the requested house geometry. Astronomy civil-year support alone does not establish the narrower chart domain. See chart limits. Historical input research, sidereal charts, transits/returns, relationship charts, additional objects, interpretation and a chart-wheel UI are outside this release.
